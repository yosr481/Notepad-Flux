1 · Pull the Session Store out of the React context

Strong

Files: src/context/SessionContext.jsx (504 lines), src/services/storage.js

Problem. One file holds five unrelated jobs: (a) React state for tabs / activeTabId / settings / recentFiles, (b) the Web Locks "primary window" election, (c) the promotion + disk-merge algorithm, (d) a debounced-save timer map, (e) beforeunload/visibilitychange flush and tabOrder metadata writes. Six useEffects. Three refs (currentTabsRef, currentActiveTabIdRef, saveTimers) exist only to dodge stale closures in the []-dep election effect. The persistence rules — "when may I write", "what wins on merge", "cancel the pending timer before deleteTab" — are smeared across createTab, closeTab, updateTab, saveTabDebounced, onPromoted, flushPendingSaves and saveSession. There is no interface for any of it — the only test surface is the whole provider driven through act() + fake locks + fake-indexeddb. The GOTCHAS list in dispatch.md ("stale closure in the election effect", "decrypt throws now") is a symptom: each entry cost a review round because the logic has no local home.

Solution. Extract a framework-free Session Store module: it owns the IndexedDB writes, the debounce map, the primary-window lock lifecycle, and the promotion/merge. Interface roughly open() · putTab(tab) · deleteTab(id) · flush() · onPromote(cb) · subscribe(cb). The "pristine tab" predicate, the disk-merge, and "cancel pending save for id" become pure functions inside it. SessionContext.jsx shrinks to a thin React adapter: hold tabs/activeTabId in state, forward mutations to the store, re-render on subscribe.

Benefits. Locality — the write rules sit in one module beside the data they guard, not in seven callbacks. Leverage — queued tasks 8 (gate tabOrder write), 9 (close-path save-failure toast), 14 (debounce saveMetadata), 15 (atomic tabs+metadata txn) each become an edit to one module with a real test surface. Tests — merge, pristine-detection and debounce-cancel become plain function tests: no act(), no jsdom, no fake locks.

BEFORE — one shallow-wide module, logic smeared

useState ×6 + useRef ×3 + useEffect ×6
lock election + onPromoted merge (90 lines)
saveTabDebounced · flushPendingSaves · saveSession
write-rule fragments in createTab/closeTab/updateTab
test surface: whole provider via act() + fakeLocks + fake-idb

AFTER — thin adapter over a deep store

SessionContext.jsx · ~120 lines (React glue)
sessionStore.js — open/putTab/deleteTab/flush/onPromote
pure: mergeDiskAndLocal(disk, local)
pure: isPristine(tab) · cancelPending(id)
test surface: call the functions directly
Overlaps queued Task 24 ("split SessionContext into settings/tab-state/actions contexts"). This goes deeper: 24 splits the React contexts by concern; this pulls the non-React engine out entirely so the split contexts have something testable to sit on. Do this first, then 24 is trivial.

2 · Deep "Save Policy" module; trim the shallow drivers

Worth exploring

Files: src/utils/fileSystem.js (332 lines, 3 drivers × ~7 methods), src/hooks/useCommands.js (saveFile, saveFileAs, closeTab save-branch, closeWindow save-branch)

Problem. fileSystem.js is three driver objects whose methods are near-identical: picker → createWritable → write → close, each wrapped in the same try/catch with AbortError → null. The public fileSystem.* facade is as wide as the impl and just forwards to getDriver() — a shallow module. The logic that actually has bugs — the ladder "fileHandle? save in place · else !isSupported() && filePath? saveFileAs to path · else saveFileAs to title", then patch title/filePath/fileHandle/isDirty back onto the tab — is copy-pasted four times in useCommands.js. That is exactly what queued Task 22 names ("extract persistTab() + canSaveInPlace()").

Solution. Collapse each driver to the primitives that genuinely differ (~3: pickOpen, pickSave, writeTo); fold the repeated AbortError→null + logging into one wrapper. Add one deep module — Save Policy — exposing persistTab(tab, content) → { tab, saved } and canSaveInPlace(tab). The four call sites shrink to const { tab, saved } = await persistTab(t, content).

Benefits. Locality — the strategy choice and the tab-field patching that follows it live together, so you can see the branches you're choosing between. Leverage — queued Task 9's "save-failure toast + requestPermission" is one edit, not four. Tests — persistTab is table-testable over (fileHandle, filePath, isSupported); today those paths are only reachable by driving the whole command hook with mocked pickers.

BEFORE

fileSystem.js — 3 × 7 wrapped methods (wide facade)
useCommands: save ladder ×4 (saveFile, saveFileAs, closeTab, closeWindow)
each re-patches title/filePath/fileHandle/isDirty by hand

AFTER

fileSystem.js — 3 × ~3 primitives + 1 error wrapper
savePolicy.js — persistTab() · canSaveInPlace()
4 call sites → one line each

3 · One home for the "reveal on cursor" rule + the debounced-decoration skeleton

Worth exploring

Files: src/extensions/livePreview.js (isCursorTouching / isCursorOnLine, ~25 call sites), src/extensions/linkPreview.js (its own copy of isCursorTouching + its own debounce timer), src/extensions/imagePreview.js (its own debounce timer), src/extensions/widgets.js

Problem. "Show raw markdown when the cursor is on or inside this range, otherwise render it" is the signature behaviour of the whole editor — and it is written three times. linkPreview.js has a second, subtly different isCursorTouching. imagePreview.js and linkPreview.js each hand-roll the same ViewPlugin + this.debounceTimer = setTimeout(...) skeleton, which is what queued Task 21 names ("extract makeDebouncedDecorationPlugin factory"). Adding a fourth preview extension means copying the skeleton again, and there is no single test that pins the reveal rule.

Solution. src/extensions/selection.js — deep helper exposing isCursorTouching, isCursorOnLine, and a small revealsFor(node, selection). makeDebouncedDecorationPlugin({ build, delay }) for the ViewPlugin skeleton. Each extension then supplies only its node matcher and its widget.

Benefits. Locality — the reveal rule has one definition and one test file. Leverage — queued Task 6 ("scope decoration build to viewport + changed ranges") becomes a change to the factory, not to every extension. AI-navigability — "how does reveal-on-cursor work" resolves to one file instead of three near-copies.

BEFORE

livePreview.js — isCursorTouching / isCursorOnLine
linkPreview.js — 2nd isCursorTouching + own debounce
imagePreview.js — own debounce ViewPlugin

AFTER

selection.js — isCursorTouching · isCursorOnLine · revealsFor
makeDebouncedDecorationPlugin({ build, delay })
livePreview / linkPreview / imagePreview — matcher + widget only

Top recommendation — start with Candidate 1

SessionContext.jsx is the hottest file in recent history (every P0 in the build-loop queue lands there), the hardest to test (needs act() + fake locks + fake-indexeddb just to reach the logic), and the one place where a real seam is missing — React state on one side, a persistence engine on the other. Pulling the Session Store out concentrates the merge / debounce / write-rule complexity into one module with a plain-function test surface, and de-risks queued tasks 8, 9, 14, 15 and 24 before they're written. Candidates 2 and 3 are worthwhile and already half-scoped in the queue (Tasks 22, 21, 19) — but they're lower-blast-radius and can follow.

Interfaces are intentionally not designed here — that's the next step, per candidate you pick.
